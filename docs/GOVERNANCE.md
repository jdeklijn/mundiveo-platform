# Governance (Draft)

**Status: draft, pre-community.** Right now there is one person driving the project. This document describes the intent for how decision-making should evolve as contributors join — it is not yet in force, and will itself be one of the first things opened up for community feedback.

## Principles

1. **Transparency by default.** Design discussions, trade-offs, and disagreements should be visible (video, GitHub Discussions, issues) rather than resolved privately wherever possible.
2. **Community input on scope decisions, not just code review.** Whether to build a feature at all (e.g. the 18+ question, decentralized storage) is treated as a governance decision, not just an engineering one.
3. **A core team retains operational responsibility.** Inspired by how the Linux kernel is run: broad community input, but a smaller group is accountable for keeping the project shippable, secure, and legally sound.

## What's undecided (to be shaped with early contributors)

- Formal proposal/voting process (e.g. lightweight RFC process vs. informal consensus)
- Criteria for who gets commit access / maintainer status
- How disputes get resolved if consensus doesn't emerge
- Relationship between the core team and any future legal entity (foundation, cooperative, company) that ends up holding the project

## Why this document is short right now

Writing an elaborate governance charter before there's a community to govern tends to produce rules nobody asked for. This will grow as real contributors join and real decisions need a process.
